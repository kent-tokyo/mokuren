**mokuren — 音楽理論的な判断を探求するための、高速で説明可能な記号的作曲エンジン。**

mokurenはコモンプラクティス様式の和声付けを生成・探索し、なぜその和音を選んだのかを*説明*できます。事後にLLMへ理由を語らせるのではなく、探索自体が生成した構造化された理由トレースを読み取ることで実現しています。

> v0.1のステータス: 縦割りの1本のスライスがエンドツーエンドで動作します — 長調の固定ソプラノ旋律に対するSATB和声付けで、`explain()`・`why()`・`why_not()`は実際に評価された候補データに裏付けられています。このスライス以上の用途に頼る前に、[現在の制限](#現在の制限)を読んでください。

**[ブラウザでmokurenを試す →](https://kent-tokyo.github.io/mokuren/playground/)** — Rustをコンパイルしたライブデモです(サーバー不要)。旋律を和声付けして、mokurenが検討したすべての候補について`why()`/`why_not()`をクリックしながら確認できます。

## mokurenが何であるか

- **候補探索型ハーモナイザー**: 旋律の各音に対してダイアトニックな和音+声部配置の候補を生成し、コモンプラクティスのルールに照らしてスコアリングし、ビームサーチで最良の連鎖を探索します。
- **説明可能な推論エンジン**: 採用・却下を問わず、すべての候補は構造化された`ScoreBreakdown`と`Vec<Reason>`を持ちます — 単なる数値ではありません。`why()`と`why_not()`はそのデータを直接読み取って返します。
- **決定的**: 同じ入力・同じルールなら常に同じ出力になり、明示的なタイブレークの連鎖(スコア → 声部進行コスト → 正準ローマ数字順 → 正準声部配置順)を持ちます。ランキング処理のどこにも`f64::partial_cmp().unwrap()`は使っていません。

## mokurenが何でないか

- DAWでもシンセサイザーでもオーディオエンジンでもありません — mokurenはオーディオに一切触れません。`AGENTS.md`のセクション19/27を参照してください。
- 記譜エディタでもMIDI/MusicXMLエクスポーター(まだ)でもありません — v0.1は構造化されたシンボリックな結果までです。[ロードマップ](#ロードマップ)を参照してください。
- LLM駆動の作曲ツールではありません — LLMをmokurenの前段に置いて自然言語インターフェースとして使うことはできますが、mokurenの音楽理論的な推論そのものがLLMに依存することはありません。
- 「どんなスタイルでも何でも和声付けできる」汎用ツールではありません — v0.1は1つのスタイル(`Style::CommonPractice`)、1つのモード(長調・短調)、1つの声部配置(SATB)のみです。

## 最小サンプル

```rust
use mokuren::prelude::*;

fn main() -> Result<()> {
    let melody = Melody::parse("C4 C4 G4 G4 A4 A4 G4")?;

    let result = Composer::new()
        .key(Key::C_MAJOR)
        .style(Style::CommonPractice)
        .voices(Voices::SATB)
        .search(BeamSearch::new().width(32))
        .harmonize(melody)?;

    println!("{}", result.explain());
    Ok(())
}
```

自分で実行するには: `cargo run --example basic`

## 説明可能性のサンプル

```text
Harmonization in C major

Position 0: I (score +0.30)
Position 1: IV64 (score +1.11)
Position 2: V6 (score +1.46)
Position 3: I (score +1.76)
Position 4: vi (score +1.03)
Position 5: IV (score +1.28)
Position 6: I (score +2.21)

Progression: I - IV64 - V6 - I - vi - IV - I
```

2番目の和音がなぜ`V6`なのかを尋ねると:

```text
Why V6?

+ voice leading: 13 semitones of motion, 0 common tone(s), contrary motion: true: +0.25
+ harmonic function: predominant -> dominant: +0.80

Final local score: 1.46
```

## `why_not`のサンプル

```text
Why not iii?

iii was valid and ranked #6.

+ voice leading: 18 semitones of motion, 0 common tone(s), contrary motion: true: +0.25
+ harmonic function: predominant -> tonic: +0.20

Final local score: 0.81
Difference from selected V6: -0.65
```

`why_not`は、ビームサーチが最後まで生き残らせなかった候補(そのstatusに*なぜ*却下されたか — どの`RuleId`が発火したか — が示されます)や、その位置ではそもそも合法でなかったローマ数字についても答えます(パニックではなく、きれいなエラーとして)。

診断情報は決定ごとではなく集計です — 上記の実行から得た実際のカウント、ビーム幅32時点のもの:

```text
Candidates generated: 100864
Candidates retained:  3686
Candidates rejected:  97178

Top rejection reasons:
voice overlap 74772
missing chord tone 67720
voice crossing 51114
unprepared six-four 18360
spacing 16980
```

## 対応している理論(v0.1)

- **調性**: 長調・(自然的+和声的)短調に対応、ダイアトニックな音階度数を正しく綴ります。半音的変化は副次(セカンダリー)ドミナント(下記)のみに限定されています — モーダルミクスチャー、ナポリの和音、増六の和音などはまだありません。
- **和音**: 長・短・減三和音、属七の和音、転回形あり(三和音: 根音位置/6/64、V7: 根音位置/65/43/42)。
- **ローマ数字**: I, ii, iii, IV, V, V7, vi, vii°、加えてx∈{ii, iii, IV, V, vi}に対する副次(セカンダリー)ドミナント V/x, V7/x(例: `V/V`, `V7/vi`)。短調では: 自然短調の各ダイアトニック三和音、導音を半音上げた和声的短調のV, V7, vii°、x∈{ii, IV, V, vi}に対する副次ドミナントV/x, V7/x、第6音を半音上げた旋律的短調由来のii・IVの代替コードにも対応しています。`HarmonicFunction`(トニック/プレドミナント/ドミナント)はローマ数字そのものとは別の概念として保持されています。
- **声部**: 従来的なデフォルト音域を持つSATB。
- **ハード制約**: 音域、声部交差、声部重複、並行5度/8度/ユニゾン、間隔、和音構成音の欠落、導音の重複、導音の解決、七の音の解決、準備なしの六四の和音、副次ドミナントの解決。
- **ソフトプリファレンス**: 声部進行の質(共通音、反行)、旋律的動き(順次進行への報酬/跳躍へのペナルティ)、和声機能の進行、終止のサポート、重複プリファレンス、同一和音の反復に対するペナルティ。
- **探索**: ビームサーチ、決定的なタイブレーク、位置ごとの診断情報。

## 現在の制限

出力を信頼する前に読んでください。優先順位順に:

1. **バッハコラールのフルコーパスに対して、mokurenは長調コラールの大半、短調コラールも過半数を和声付けできます。** 348曲のベースライン(music21が長調・短調のいずれかに解決するすべてのRiemenschneiderコラール、`tools/music21_chorale_extractor.py`による)では**長調で94.5%のカバレッジ**(172/182)、**短調で64.5%**(107/166)という結果でした。ハードルール違反はどちらも0件です — 詳細は`BENCHMARK.md`と`tasks/baseline-v0.5.0-minor-applied-dominants.md`を参照してください。短調の語彙は長調からのコピーではなく実コーパスの証拠から選びました: 短調の失敗をビセクションした結果、到達不能なソプラノの音はすべて副次ドミナント(x∈{ii, IV, V, vi}に対するV/x, V7/x — V/IIIは対象外、必要とする証拠がゼロだったため)か旋律的短調の上げた第6音(iiとIVの代替コードとして)のどちらかで説明でき、両方を実装したことで短調のカバレッジが42.8%から向上しました。短調の残りのギャップは、今では和音が存在しないことよりも探索の幅の問題が中心です。長調の残り10件の失敗は: 7件が探索の限界(より広いビームなら経路が見つかります、項目4参照)、3件が本当に未修正のギャップです — ソプラノの音が形式上の七の音としての役割を強いられ、順次下行で解決すべきところ、実際の旋律は3度跳躍しています。おそらくバッハがその音を装飾的な非和声音(経過音)として使っているためで、mokurenにはそのモデルが一切ありません(現状すべてのソプラノの音は完全な和音構成音でなければなりません)。
2. **ソプラノの休符は、直接モデル化されるのではなく、旋律を独立したフレーズへ分割します。** `Melody`/`Composer::harmonize`は今も休符のないプレーンな音符列しか扱いません — 新しい`MelodyLine`型(`src/melody.rs`)が`Note`/`Rest`イベントを保持し、その`phrases()`メソッドが各休符で連続した音符の連なりに分割し、それぞれ独立に和声付けします(息継ぎの休符が実際に果たす役割 — 1つの和声的アイデアの中の隙間ではなくフレーズの境界 — と一致します)。これにより和声付け可能なコーパスが144曲から182曲(+38)へ拡大し、元の144曲への回帰は0件でした。できないこと: 完全なフレーズの区切りでは*ない*休符のモデル化(例えば実際には和声的な連続性がある休符もやはり分割されてしまいます)、声部進行/並行進行ルールがフレーズ境界をまたいで見ることはありません(各フレーズはそれ自体が独立した短い曲であるかのように新しく始まります) — 実際に問題になるかはまだ分かっておらず、検証もされていません。
3. **六四の和音(第二転回形三和音)の扱いは、真の係留六四検出ではなく、後ろ向きのヒューリスティックです。** バスがペダル(直前のバスと同じ)であるか、順次進行でアプローチされている場合にのみ六四の和音を受け入れます。前方を見てその和音が実際にVへ解決するかを確認することはできず、最初の和音として六四が来ると無条件に拒否します(比較対象となる直前のバスがないため)。上記のベースラインでは、**このルール単独が原因の失敗は0件**でした — 実在する制限ではありますが、現在のボトルネックではありません(`ROADMAP.md`参照)。
4. **ビームサーチにはホライズン効果があります。** `CadenceSupportRule`は最終位置のみに報酬を与えるため、ビームが狭すぎると、その報酬に到達する前に最終的に最良となる経路が枝刈りされてしまうことがあります。`BeamSearch::new()`のデフォルトは幅32です。副次ドミナントの語彙(項目6)が各位置で検討される候補数をほぼ倍増させたことで、このホライズン効果は実測できるほど悪化しました — v0.1.0ベースラインで幅32で和声付けできていた2曲のコラールが、今は広いビームを必要とします(1曲は幅64で、もう1曲は幅512で回復。これは推測ではなく直接確認済みです — `tasks/baseline-v0.2.0-secondary-dominants.md`参照)。デフォルト幅は意図的に32のままにしてあり、幅512のケースをカバーするために引き上げてはいません — それは全員にとって稀なケースを高コストにしてしまうためです。この構築中に見つかった関連するケース(幅だけでなく*スコアリング*のバグ)については`tasks/lessons.md`を参照してください。より長い、あるいはより和声的に曖昧な旋律に対しては幅を広げてください。
5. **スコアの重みはv0.1のデフォルト値であり、コーパスでチューニングされたものではありません。** 1つの旋律に対して手作業で調整され(`PLAN.md`参照)、音楽的に妥当な挙動に到達させたものです。項目1のベースラインは実在のコラールに対する挙動を測定していますが、それに対して重みを再調整することはしていません — これは未解決のままです。
6. **副次ドミナントは完全な副次和音理論よりも狭い範囲です。** 長調ではx∈{ii, iii, IV, V, vi}に対するV/x, V7/x、短調ではx∈{ii, IV, V, vi}のみ(V/IIIは対象外 — 難しいからではなく、実際の短調コラールの失敗をビセクションした結果、必要とする曲がゼロだったためです、`tasks/baseline-v0.5.0-minor-applied-dominants.md`参照)。どちらのモードでも副次の導音和音(vii°/x)や、副次ドミナントの副次ドミナント(連続する転調の連鎖)はありません。解決には、その半音的な音を保持するすべての声部で厳格な順次上行が必要です。`LeadingToneResolutionRule`の内声の例外(項目9)とは異なります — 実際の実務では、内声には代わりに跳躍が許されることがあります。副次ドミナントがフレーズの最後の和音として提示されることもありません(そこでは解決できないため)。
7. **旋律的短調は2つの和音に限定されており、一般的な慣習ではありません。** 上げた第6音は、代替のii(長調のiiと同様の短三和音であり、自然短調自身の減三和音ii°ではない)とIV(長三和音であり、自然短調自身の短三和音ivではない)を通してのみ提供されます — 実コーパスのデータでこの2つが重要だと分かったためです。他の和音では一切使われず、下行時に自然短調へ戻る旋律的短調本来の区別も実装していません。**その他の半音的和声(モーダルミクスチャー、ナポリの和音、増六の和音)、MIDI/MusicXML/serdeにはまだ対応していません。** すべて意図的に先送りにしています — `PLAN.md`参照。
8. **最初の位置での`why()`は薄いです。** 直前の和音がないため、ほとんどのソフトルールには比較対象がなく、`Reason`を何も生成しません。適用されるのは重複プリファレンス(理由テキストは生成しません)だけです。
9. **単一クレート、単一スタイルプロファイル。** `Style::CommonPractice`が唯一のスタイルです。`RuleProfile`/`StyleProfile`的な拡張性は型としては存在しますが、実装されているインスタンスは1つだけです。
10. **導音解決の内声例外は、実際の教育法よりも狭いです。** `LeadingToneResolutionRule`は内声(アルト/テノール)が上行解決の代わりに順次下行または3度下行して和音を完成させることを許していますが、この例外は無条件です — 実際の実務では、上行解決すると和音が不完全になる、あるいは悪い重複を強いる場合にのみこの例外を認めますが、このルールはそれをチェックしていません。`ChordalSeventhResolutionRule`と`SecondaryDominantResolutionRule`にはどの声部にもこのような例外はありません(前者については実際の実務もおおむね一致しますが、後者はv0.1の単純化です — 項目6)。
11. パフォーマンスについては、副次ドミナントの語彙追加より前の(リリースビルド、この機材、この1コミット時点での)測定値が1つだけあります: `cargo bench` — 1つの位置での候補生成は約480µs、デフォルトビーム幅(32)での7音の和声付け全体は約212ms、ビーム幅・旋律長のいずれに対してもほぼ線形にスケールします — 現在の語彙に対しては再測定していません。時系列や機材をまたいでの追跡はしておらず、タグライン自体(`AGENTS.md`セクション23)を超えて「速い」という主張を組み立てる根拠にもしていません。項目1のベースラインには現在の実コーパスでの実行時間があります: 幅32で中央値1.4秒/コラール(p90 1.9秒) — コーパスが大きくなったにもかかわらずv0.2.0ベースラインの中央値2.9秒より低い値です(異なる実行での計測です。フレーズ分割(項目2)が38の複数フレーズコラールに寄与している可能性はありますが、単一フレーズが大半を占め、それらはv0.2.0と同一の処理を行っているため、完全には説明しきれていません — 回帰ではなく有益な方向のため、これ以上は追及していません)。
