# mokuren v0.2.0-in-progress major-mode chorale baseline (secondary dominants + soprano-range fix + prolongation fix)

Generated by `examples/chorale_benchmark.rs` against the same 144 chorales as [`tasks/baseline-v0.1.0.md`](baseline-v0.1.0.md) (re-extracted locally via `tools/music21_chorale_extractor.py`, identical corpus). Titles, catalog numbers, and mokuren's own computed statistics only — no encoded musical content — same non-vendoring stance as v0.1.0 (BENCHMARK.md).

**Comparison against `tasks/baseline-v0.1.0.md`**: coverage rose from 50.7% (73/144) to **94.4% (136/144)** — +43.7pt absolute, +86% relative. 0 hard-rule violations, same invariant as v0.1.0. This is the second measurement of the secondary-dominant work — an earlier same-day run (BENCHMARK.md's "v0.2.0-in-progress baseline" section) found 91.7%; a bisection pass over the 6 chorales that measurement left classified `Other` (undiagnosed) found and fixed one more real bug, adding +2.7pt on top.

**The bisection, and what it found** (full detail in PLAN.md/`tasks/lessons.md`): the harness's own failure-diagnosis tool had a bug — it bisected by harmonizing *truncated* melodies directly, which made the truncation point look artificially final to the search, wrongly triggering `SecondaryDominantResolutionRule`'s "no applied dominant at the final position" rule (and `CadenceSupportRule`) at positions that aren't actually final in the real piece. Fixed by replaying the *full* melody's search up to the actual failure point instead (`replay_to_failure`, `examples/chorale_benchmark.rs`). With that fixed, bisecting the real 6 failures found:

- **3 of 6** (Riemenschneider 102, 173, 327) shared one root cause: a chromatic tone (an applied dominant's own chromatic tone, e.g. D#5 in Riemenschneider 102) *held or repeated* across two consecutive notes before resolving. `SecondaryDominantResolutionRule` required resolution at the *very next* position unconditionally, so the second occurrence of the held note had nowhere valid to go. Fixed: prolonging the *same* applied dominant (same tonicized target) across a repeat is no longer treated as an unresolved dangling dominant — the resolution obligation only applies once the harmony actually changes away from it. This is the fix that added the +2.7pt.
- **2 of 6** (Riemenschneider 40, 202) share a different, *not yet fixed* cause: the soprano is fixed on what the vocabulary can only interpret as a formal chordal seventh (of an applied-dominant-seventh chord), which must resolve down by *step* — but the actual melodic motion is a *leap* of a third. This is very likely Bach using the note as a decorative non-harmonic tone (a passing tone or similar), which mokuren has no concept of at all (every soprano note is currently required to be a full chord tone). Real feature gap, not a quick fix — tracked in `tasks/todo.md`, not attempted this pass.
- **1 of 6** (Riemenschneider 234) turned out to be beam-width-recoverable after all once the width-512 retry ceiling was added to the harness's own classification ladder — not a genuine structural bug.

**Regression check** (unchanged conclusion from the first measurement, re-verified): per-chorale diff against v0.1.0 found 2 chorales (Riemenschneider 135, 230) that succeed at width 32 in v0.1.0 and don't now — both directly confirmed to still succeed at a wider beam (64 and 512 respectively), the same known vocabulary/beam-width trade-off as before, not a new correctness problem. The default beam width (32) stays unchanged.

Reproduce: `python3 tools/music21_chorale_extractor.py -o <dir>` then `cargo run --release --example chorale_benchmark -- <dir> --report tasks/baseline-v0.2.0-secondary-dominants.md`. To bisect one chorale directly: `cargo run --release --example chorale_benchmark -- <dir> --bisect "<name substring>"`. Extracted `.chorale` files are never committed (deleted after each run, per "reference, don't vendor").
